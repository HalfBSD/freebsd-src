
Audit the entire HalfBSD source tree and identify additional subsystems, functionality, compatibility layers, utilities, protocols, drivers, libraries, daemons, boot mechanisms, and infrastructure that are candidates for complete removal.

Do NOT make changes yet. This is an architectural audit. I want a prioritized list of things that do not fit HalfBSD's intended purpose.

HalfBSD is NOT intended to be a general-purpose FreeBSD distribution that supports every historical FreeBSD use case.

HalfBSD is a deliberately opinionated, aggressively simplified FreeBSD-derived workstation operating system.

Assume the following design goals:

- amd64 only.
- Modern x86-64 hardware.
- UEFI-only boot.
- ZFS-only root/storage model.
- Primarily a physical workstation OS, not a guest OS intended to run under arbitrary hypervisors.
- bhyve is the preferred virtualization mechanism when virtualization is needed.
- Modern Wayland graphical desktop, especially sway/niri-style environments.
- AMD graphics are an important target.
- Normal workstation networking: Ethernet/Wi-Fi, DHCP, DNS, IPv4, SSH, NTP, web browsing, package management, NFS, etc.
- IPFW is the firewall.
- Local virtualization may use an internal private network/NAT.
- The machine may act as an NFS client and may provide simple LAN services, but it is not intended to be a general enterprise server platform.
- Preserve the core Unix/POSIX programming environment: kernel APIs, system calls, libc, processes, files, sockets, pipes, signals, permissions, shell access, development tools, etc.
- Preserve functionality useful for software development, system administration, debugging, recovery, package building, and maintenance.
- Do not preserve something merely because it is historically associated with Unix or because upstream FreeBSD supports it.

Look especially for functionality belonging to these categories:

1. Legacy hardware support
   - Hardware unlikely to exist in a modern amd64 workstation.
   - Obsolete buses, controllers, networking hardware, storage systems, input devices, terminal hardware, modem/dialup hardware, old console systems, etc.

2. Enterprise/datacenter functionality
   - SAN infrastructure.
   - Fibre Channel.
   - RDMA/InfiniBand.
   - large-storage-array support.
   - clustering/high-availability systems.
   - enterprise authentication/integration facilities.
   - carrier/telecom functionality.
   - features whose realistic use case is a large server installation rather than a workstation.

3. Server functionality
   - Daemons and protocols whose primary purpose is turning the system into a network server.
   - Especially old or niche network services.
   - Do not flag SSH, ordinary NFS functionality, DNS client functionality, DHCP client functionality, or basic networking simply because they involve networking.

4. Obsolete or historical networking
   - Old protocols.
   - Compatibility protocols.
   - RPC services with little relevance to the HalfBSD workstation.
   - dialup-era networking.
   - obsolete network configuration mechanisms.
   - redundant firewall implementations.
   - unusual routing/network-appliance functionality that does not support our VM/NAT or workstation requirements.

5. Compatibility layers
   - Compatibility for obsolete operating systems, ABIs, executable formats, architectures, kernel interfaces, or hardware.
   - Old application compatibility retained only for historical reasons.
   - Hypervisor guest support that HalfBSD does not need.

6. Alternate boot/install environments
   - BIOS/legacy boot.
   - PXE/network boot where not required by HalfBSD.
   - Xen/other hypervisor guest boot mechanisms.
   - alternate root filesystem boot paths we no longer support.
   - installer infrastructure designed to support configurations HalfBSD forbids.

7. Alternate storage architectures
   - Filesystems, volume managers, RAID systems, storage transports, and storage administration systems that make little sense in a ZFS-focused workstation.
   - Be careful to distinguish things needed for removable media/interoperability from things intended as native system storage.

8. Old multiuser/centralized Unix infrastructure
   - Features designed for terminal farms, centralized Unix account management, university timesharing systems, old network directory systems, remote login systems, disk quotas, accounting, etc.
   - Do not assume that something must remain simply because POSIX or historical Unix systems commonly included it.

9. Redundant utilities
   - Multiple programs solving essentially the same problem.
   - Ancient utilities superseded by another utility we already retain.
   - Tiny historical commands that provide application-level convenience but no meaningful OS capability.
   - Utilities primarily useful for protocols/subsystems we have already removed.

10. Orphaned functionality
    - Source left behind after previous HalfBSD removals.
    - Libraries with no remaining consumers.
    - headers/API definitions for removed subsystems.
    - unused build options.
    - unused rc scripts.
    - unused configuration files.
    - manual pages for removed functionality.
    - kernel options/drivers that no longer have consumers.
    - compatibility glue whose original subsystem has disappeared.

11. Excessive abstraction or configurability
    - Infrastructure whose purpose is to support many mutually exclusive configurations when HalfBSD deliberately chooses one.
    - Plugin architectures that only exist to support functionality we don't intend to ship.
    - generic framework code whose only remaining consumers could be replaced by a much simpler HalfBSD-specific implementation.

12. Security/maintenance liabilities
    - Network-facing functionality we do not need.
    - privileged daemons we do not need.
    - parsers for obsolete protocols/formats.
    - setuid/setgid programs that provide little value.
    - large compatibility layers that substantially increase attack surface.
    - components that create substantial maintenance burden for negligible HalfBSD benefit.

13. Build infrastructure for things we no longer ship
    - build glue.
    - makefiles.
    - options.
    - tests.
    - generated headers.
    - libraries.
    - documentation.
    - tools existing exclusively to support removed components.

Do not equate "old" with "bad." Some very old Unix functionality is fundamental and should remain.

Likewise, do not recommend removing something merely because the typical desktop user doesn't invoke it directly. Kernel infrastructure, libc functionality, debugging facilities, build tools, recovery tools, hardware enumeration, filesystem repair/recovery, networking diagnostics, and dependencies of important applications may still be essential.

For every candidate, determine the dependency chain before recommending removal.

For each candidate provide:

- Name of subsystem/functionality.
- What it does.
- Major source-tree locations.
- Why FreeBSD contains it.
- Why it does or does not fit HalfBSD.
- What currently depends on it.
- Whether those dependencies are themselves removal candidates.
- Whether removal affects kernel ABI, libc ABI, ports/packages, bhyve, Wayland, browsers, audio, networking, ZFS, SSH, NFS, pkg, or development tools.
- Whether it can merely be excluded from the build or whether the source can safely be deleted.
- Expected reduction in complexity/attack surface/build size if removed.
- Risk of removal.
- Confidence level.
- Tests/build configurations that should be performed after removal.

Organize findings into:

A. Strong removal candidates
Functionality with essentially no legitimate HalfBSD use case and limited dependency risk.

B. Likely removal candidates requiring dependency cleanup
Things that fit our removal philosophy but have nontrivial consumers or source-tree tentacles.

C. Simplification/refactoring candidates
Things we probably still need, but where FreeBSD's implementation is much more general than HalfBSD requires.

D. Keep
Things that may initially look removable but provide an important workstation, development, recovery, virtualization, security, or compatibility function.

E. Investigate further
Things where the dependency or practical consequence isn't yet clear.

Prefer removing entire coherent subsystems rather than deleting isolated files merely to reduce line count.

Think in terms of architectural capability rather than filenames. Ask:

"If HalfBSD had been designed from scratch specifically as a modern single-workstation FreeBSD-derived OS, would we deliberately add this functionality?"

If the answer is no, determine whether anything HalfBSD actually needs still depends on it.

Be aggressive in identifying candidates, but conservative about declaring a removal safe without tracing dependencies.

Do not modify the tree during this pass. Produce the audit first.
