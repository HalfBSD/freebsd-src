### E2. Tape, media-changer, and remote-tape support

**Purpose and locations:** Review and remove FreeBSD’s magnetic-tape, automated media-changer, and remote-tape infrastructure. Primary candidates are the `sa` sequential-access tape driver, `ch` media-changer driver, `mt`, `tcopy`, `rmt`, `libmt`, associated kernel modules, headers, build integration, documentation, tests, and configuration. The original E2 also grouped modern SAS HBAs and enclosure services with tape support; **those are explicitly outside this removal scope and must be preserved.** HALFBSD-ARCHITECTURAL-AUDIT

**HalfBSD policy:** HalfBSD supports modern direct-attached storage suitable for ZFS, including SATA, NVMe, USB mass storage, SAS disks, and modern SAS HBAs. It does not need to function as a magnetic-tape backup workstation or control automated tape libraries.

Tape support should therefore be removed as a coherent capability rather than using the age of a particular storage controller as the criterion.

### Approved removal targets

Remove functionality dedicated to magnetic tape and tape-library operation, including:

- `sa` — SCSI sequential-access/tape devices;
- `ch` — SCSI media changers and robotic tape-library mechanisms;
- `mt` — tape positioning/control utility;
- `tcopy` — tape-copying and tape-record inspection utility;
- `rmt` — historical remote magnetic-tape service/protocol;
- `libmt` where it exists solely to support retired tape functionality;
- tape-specific kernel modules and device configuration;
- tape/changer-specific ioctl definitions where no retained consumer requires them;
- tape-specific rc/configuration integration;
- tests, manual pages, examples, headers, package metadata, and installed-file entries belonging exclusively to the removed functionality.

### Explicitly preserve modern SAS storage

Do **not** remove or weaken:

- `mps`;
- `mpr`;
- `mpi3mr`;
- CAM core;
- SCSI disk support;
- ordinary SAS/SATA disks exposed through those HBAs;
- passthrough functionality required for modern disks;
- ZFS use of SAS-attached disks;
- disk discovery and device management through CAM;
- `camcontrol`;
- `camdd` disk/block-device functionality;
- bhyve storage functionality relying on retained CAM interfaces.

Modern SAS HBAs can expose individual disks directly to ZFS and therefore fit HalfBSD’s workstation/storage model even though some of the same controllers are also capable of attaching tape hardware. The existence of tape support behind an HBA is **not** grounds to remove the HBA. The original audit explicitly recognizes modern SAS HBAs as legitimate direct-storage devices. HALFBSD-ARCHITECTURAL-AUDIT

### Explicitly preserve enclosure services

Preserve:

- `ses`;
- `sesutil`;
- SCSI enclosure-services support;
- enclosure status, slot identification, fault LEDs, temperature/status reporting, and other functionality useful with direct-attached SAS disk enclosures.

Enclosure support is not inherently tape-specific. A ZFS workstation or storage machine may legitimately use a SAS HBA connected to a multi-disk enclosure.

Treat SES as a separate storage-management capability, not as collateral tape infrastructure.

### `camdd` / `libmt` dependency

The original audit found that `camdd` links against `libmt`; therefore `libmt` must **not** simply be deleted without tracing that dependency. HALFBSD-ARCHITECTURAL-AUDIT

Before modifying `libmt`, determine exactly which `camdd` functionality depends on it.

If the dependency exists only to support tape-specific operations:

- remove or isolate those tape-specific paths;
- refactor `camdd` so its ordinary disk/block-copy functionality remains intact;
- then remove `libmt` if it has no retained consumer.

If `libmt` provides generally useful functionality required by retained disk operations, preserve or relocate the necessary portion rather than deleting it merely because its name is associated with tape.

**Do not remove `camdd` as part of E2.**

### Hardware audit requirement

Before removing the kernel drivers, confirm that:

- `sa` serves only sequential-access/tape-class devices;
- `ch` serves only media changers/library robotics;
- no retained optical-disk, SAS-disk, USB-storage, enclosure, or bhyve path uses these drivers;
- shared CAM/SCSI infrastructure is not being mistaken for tape-specific infrastructure.

The audit should distinguish:

```text
CAM
├── disk devices                    KEEP
├── pass-through                    KEEP
├── SAS HBA support                 KEEP
├── enclosure services              KEEP
├── optical devices                 KEEP
├── sequential-access tape          REMOVE
└── media changers                  REMOVE
```

### Optical-media protection

Tape removal must not affect:

- SATA CD/DVD/Blu-ray drives;
- USB optical drives;
- CAM CD/DVD device handling;
- software playback/ripping of CDs;
- DVD/Blu-ray data access.

A SCSI-family command interface being shared between tapes and optical/storage devices is not authorization to remove the shared CAM or SCSI layers.

### Remote-tape policy

`rmt` should be removed entirely. HalfBSD does not need the traditional Unix abstraction of exposing a tape drive remotely to another host.

This is consistent with the broader HalfBSD policy that networked data movement should occur through explicit application-level protocols rather than making remote hardware appear locally attached.

### Disposition and impact

After E2, HalfBSD should still support:

```text
NVMe SSD
SATA SSD/HDD
USB storage
SAS SSD/HDD
modern SAS HBAs
disk enclosures / SES
optical drives
ZFS
CAM administration
```

but no longer support:

```text
magnetic tape drives
tape positioning/control
automated tape libraries
media changers
remote-tape protocol
tape-copy utilities
```

### Benefit / risk / confidence

Moderate reduction in specialized kernel drivers, utilities, protocol support, and historical backup infrastructure. Low architectural risk once tape-specific dependencies are isolated. The main integration risk is accidental removal of shared CAM functionality or `camdd` functionality through `libmt`.

High confidence in retiring tape and changer functionality; high confidence in preserving modern SAS HBA and enclosure functionality.

### Validation

After removal, validate at minimum:

- clean world/kernel/all-retained-modules build;
- SATA disk discovery and I/O;
- NVMe operation;
- USB mass storage;
- USB/SATA optical drives;
- `mps`, `mpr`, and `mpi3mr` module build/load;
- SAS disk discovery;
- `camcontrol`;
- retained `camdd` disk-copy operations;
- SES enclosure discovery and `sesutil`;
- ZFS pool import, scrub, resilver, SMART/passthrough where applicable;
- bhyve storage backends;
- absence of `sa`, `ch`, `mt`, `tcopy`, `rmt`, and other retired tape artifacts after installation.

This version makes the boundary much cleaner: **HalfBSD is allowed to be a serious ZFS machine with SAS HBAs and disk shelves; it just isn't a tape workstation.**
